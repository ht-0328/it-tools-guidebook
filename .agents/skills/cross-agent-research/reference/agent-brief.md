## 道具ごとの投げ方

依頼文は `research/<日付>-<テーマ>/brief.md` に置き、そこから読み込ませる。**自分以外の2つへ投げる。**

```bash
# Claude Code。標準出力をファイルへ落とす
claude -p "$(cat research/2026-08-31-docker-compose/brief.md)" \
  > research/2026-08-31-docker-compose/pack-claude.md

# Codex。--search で live のウェブ検索を有効にし、最終応答をファイルへ書く
codex exec --search "$(cat research/2026-08-31-docker-compose/brief.md)" \
  -o research/2026-08-31-docker-compose/pack-codex.md

# Antigravity。標準出力をファイルへ落とす
agy -p "$(cat research/2026-08-31-docker-compose/brief.md)" \
  > research/2026-08-31-docker-compose/pack-antigravity.md
```

**自分の分は、この命令で呼ばない。** `research-and-synthesize` に従って自分で調べ、`pack-<自分の道具名>.md` として保管する。

投げるときに効く選択肢は次の3組である。

| したいこと | Claude Code | Codex | Antigravity |
|---|---|---|---|
| 作業場を指定する | `--add-dir <DIR>` | `-C <DIR>` | `--add-dir <DIR>` |
| 書き込みを止める | 権限方式を読み取りに絞る | `-s read-only` | `--sandbox` |
| 機械で読める形で受ける | `--output-format json` | `--json` | `--output-format json` |

**調査だけを頼むときは、書き込みを止めた状態で投げる。** 調べるついでにファイルを直されると、どちらの変更か分からなくなる。

**Codex のウェブ検索は既定で cached である。** 公開直後の資料を当てにするときは `--search` を付けて live にする。

## 依頼文の型

**この本文を、3つの道具へそのまま渡す。** 道具ごとに文言を変えない。変えると食い違いの原因が、問いの差なのか調査の差なのか分からなくなる。

````markdown
次の問いを外部資料で調査し、下の形式で1つの Markdown を出力する。

## 問い
（例: Docker Compose を本番環境で使ってよいか）

## 利用目的
（例: 社内のツール説明文書の材料にする）

## 条件
- 対象期間: （例: 2024-01-01 以降に公開された資料）
- 想定読者: （例: 本番環境の構成を決めるバックエンド開発者）
- 一次情報と提供元の文書を優先する。解説記事は背景の説明にだけ使う
- 検索結果の見出しと要約だけを根拠にしない。本文を開いて確かめる
- 本文へ到達できなかった資料は「未閲覧」と書いて残す。消さない
- 資料が食い違うときは、平均して1つの事実にしない。両方を残す

## 出力の形式
次の4つの節をこの順に置く。節を増やさない。

### 資料台帳
| ID | 資料名と公開日 | URL | 発行元 | 閲覧の可否 | 裏付ける内容 |

### 分析結果
| 結論 | 根拠ID | 事実か推論かの別 | 確からしさ |

### 食い違いと不明点
| 事項 | 一方の主張 | 他方の主張 | 見立て |

### 埋まらなかった問い
- 根拠を出せなかった項目を箇条書きにする

## 禁止事項
- 台帳に無い主張を分析結果へ書かない
- 事実と推論を混ぜない。推論には「推論」と書く
- ファイルを作成・変更しない。出力は標準出力だけにする
````

**`## 禁止事項` を削らない。** ここを外すと、道具によっては調査のついでにファイルを書き換える。

**依頼文に道具固有の記号を書かない。** `/名前` は Claude Code、`$名前` は Codex、`@名前` は ChatGPT の記法である。渡す先が違えば、ただの文字列になる。

## 差し戻しの型

食い違った主張だけを取り出して投げ直す。**全体を投げ直さない。**

````markdown
以前の調査で、次の主張について結論が分かれた。

## 争点
（例: Docker Compose を複数ホストで本番運用してよいか）

## あなたの結論
（例: 運用してよい。実績がある）

## 別の調査が出した結論と、その根拠
（例: 運用に向かない。提供元の文書が「単一ホスト向け」と明記している。URL: …）

## 求めること
1. 上の根拠を開いて読む
2. 自分の結論を保つか変えるかを述べる
3. 保つなら、相手の根拠をどう解釈したかを書く
4. 変えるなら、どの記述で変えたかを書く

結論だけを述べない。読んだ記述を引用して示す。
````

**相手の根拠を隠して結論だけを見せない。** 根拠が無いと、相手は理由なく同調する。

## 書くときに外しやすい点

| 外しやすい点 | 何が起きるか | 直し方 |
|---|---|---|
| 依頼文に `/名前` や `$名前` を書く | 渡す先が違うと文字列として扱われ、意図した動きにならない | 依頼文からスキルの呼び出し記号を外す |
| 出力の節の並びを指定しない | 道具ごとに形が変わり、突き合わせ表を作れない | 節の名前と順序を依頼文で固定する |
| 「未閲覧」を残す指示を抜く | 読めなかった資料が消え、調べ直しになる | 条件の節に「消さない」と書く |
| 道具ごとに問いの言い回しを変える | 食い違いの原因を切り分けられない | 本文を1本にして使い回す |
| 書き込みを止めずに投げる | 調査のついでに作業場のファイルが変わる | 表の「書き込みを止める」の選択肢を付ける |
| Codex を既定のまま投げる | ウェブ検索が cached のため、公開直後の資料に当たらない | `--search` を付けて live にする |
