# ツール1件の説明文書を書き、一覧と検査までそろえる

**このスキルは調査しない。** 材料は `research/` の調査パックか、突き合わせ結果の `verdict.md` から取る。材料が無いなら、先に `research-and-synthesize` で作る。

**文書を1本足す作業は、ファイル2つの変更である。** `docs/<ツール名>.md` と `docs/index.md` を、同じ変更でそろえる。片方だけ直すと一覧と実体がずれる。

## 使う場面

- ユーザーが「このツールの説明文書を書いて」「調査パックから文書にして」と言ったとき
- 収録済みのツール文書を、新しい版に合わせて直すとき

**使わない場面**: 外部調査そのもの。`research-and-synthesize` と `cross-agent-research` が担う。

## 手順

写して、終わったものに印を付ける。

```text
- [ ] 手順1: 標準と型を読む
- [ ] 手順2: 材料を集め、読者と到達点を決める
- [ ] 手順3: 本文を書く
- [ ] 手順4: docs/index.md の2つの表を直す
- [ ] 手順5: 検査を通す
- [ ] 手順6: 機械で見えない箇所を自己点検する
```

### 手順1 標準と型を読む

**書き始める前に、実際にファイルを開く。** 思い出しで書かない。

| 読むファイル | 何のために |
|---|---|
| `templates/tool.md` | 節の並びと、各節に書くこと |
| `standards/engineering-docs-standard/docs/index.md` | 文書の書き方の正本 |
| `docs/index.md` | 分類の名前と、既存の収録数 |

**`standards/engineering-docs-standard/` は編集しない。** サブモジュールである。

### 手順2 材料を集め、読者と到達点を決める

調査パックの「再利用素材」の節を開く。突き合わせ結果があるなら `verdict.md` の判定を先に読む。

**冒頭のメタ情報の表を先に埋める。** 「想定読者」と「読んだあとできること」が決まらないうちは本文を書かない。

| 決めること | 決め方 |
|---|---|
| 想定読者 | 調査パックの想定読者を写す。ずれるなら、ずらした理由を書く |
| 読んだあとできること | 読者が実行できる動作で書く。「理解する」は動作ではない |
| 対象の版 | 調査した版を書く。「最新」と書かない |

**判定が「暫定」または「未確認」の主張は、その旨を本文へ書く。** 根拠の弱さを消して断定しない。

### 手順3 本文を書く

`templates/tool.md` を `docs/<ツール名>.md` へ写し、丸かっこの例文と、書き方を指示する引用行を消す。

**ユーザーが求める4点は、次の節が担う。** 節を飛ばすと、求められた内容が落ちる。

| 求められる内容 | 書く節 |
|---|---|
| 使い方と設定の方法 | 使い始める手順、よく使う操作 |
| これを使うと何がどう便利になるか | 何が変わるか |
| 使うのに最低限必要な環境とツール | 使う前に要るもの |
| どういうときに役立つか | 使いどころと、使わない場面 |

書くときに守ること。

- **「使い始める手順」には成功したときの見え方を書く。** 出力例には言語名 `text` を付ける。
- **「落とし穴」を空にしない。** 提供元の文書を読めば分かることは書かない。実際に間違えたことを書く。
- **版数を書く。** 「最新の」「今後」のような時点に依存する語を使わない。
- **リンク文字列は行き先が分かる語にする。** 「こちら」「ここ」を使わない。

### 手順4 docs/index.md の2つの表を直す

**直す表は2つある。片方だけでは終わらない。**

1. 「分類」の表: 該当する分類の収録数を1つ増やす。
2. 「収録しているツール」の表: 1行足す。並びは収録した順ではなく分類の順にする。

冒頭の「収録数は0件である」のような総数の記述も、実数に合わせて直す。

**分類は7つから選ぶ。** 版管理、開発環境、品質、自動化、運用、文書、AI である。新しい分類を足すときは、足す理由を `docs/index.md` へ書く。

### 手順5 検査を通す

```bash
bash tools/doclint.sh
```

**`error: 0` を確かめる。** `warning` は残してよい。

イメージが無いときだけ、最初に1回作る。

```bash
docker build -t edocs-tools -f standards/engineering-docs-standard/tools/Dockerfile standards/engineering-docs-standard/tools/
```

検査に落ちたら、`.doclint.yml` を書き換えずに本文を直す。**検査ルールはこのリポジトリ側で変えない。**

### 手順6 機械で見えない箇所を自己点検する

**検査を通ったことは品質の証明ではない。** 読者に合っているか、事実が正しいかは機械では判定できない。

`standards/engineering-docs-standard/docs/appendix-checklist.md` を開き、上から確かめる。加えて次の4点を見る。

- 「読んだあとできること」を、本文だけで達成できるか
- 数値と固有名詞に、調査パックの根拠IDをたどれるか
- 「扱わないこと」に、読者が期待しそうで書かなかった項目が入っているか
- 「TBD」「TODO」のような未解決の印が残っていないか

## 判定の基準

次をすべて満たせば完了とする。1つでも欠ければ未完了とする。

- [ ] `docs/<ツール名>.md` が `templates/tool.md` の節の並びに従っている
- [ ] 冒頭のメタ情報の表が埋まっている。「対象の版」に版数が入っている
- [ ] 手順3の表の4点が、それぞれ担当の節に書かれている
- [ ] `docs/index.md` の2つの表と、総数の記述が実数と合っている
- [ ] `bash tools/doclint.sh` が `error: 0` を返している
- [ ] 判定が「暫定」「未確認」の主張に、その旨が本文へ書かれている
